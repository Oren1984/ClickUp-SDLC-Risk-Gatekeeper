Why This Project Matters

Retrieval quality is the make-or-break layer of any RAG system. This lab makes it measurable.

📊
Retrieval is Measurable
Most RAG tutorials skip quantitative evaluation. This project treats retrieval as a first-class engineering concern — every configuration choice is scored against ground truth using established IR metrics.
🧰
Plug & Compare
Swap embedding providers, chunk sizes, overlap ratios, or vector stores without touching evaluation code. Provider and store interfaces are ABCs — new backends slot in by implementing three methods.
🏠
Fully Local, No Keys Required
Mock mode uses a deterministic SHA-256-seeded RNG to produce L2-normalised 384-dim vectors — no API keys, no internet, no costs. OpenAI and Gemini are optional opt-ins, not dependencies.

Core Capabilities

Modular by design — every layer is independently swappable.

✂️
Dual Chunking Strategies
Recursive chunker splits by natural boundaries (paragraphs → sentences → words → characters) before falling back. Fixed chunker splits at a configured character count with configurable overlap. Both expose ChunkingConfig for size and overlap.
  • Configurable chunk_size and chunk_overlap
  • Overlap baseline: 10–20 % of chunk_size
  • Chunker ABC — add custom strategies easily
🧰
4 Embedding Providers
Provider interface: embed(texts) -> List[List[float]]. All four providers are hot-swappable through the UI with no pipeline changes.
  • Mock — deterministic, no API key, offline
  • HuggingFace — sentence-transformers, local GPU/CPU
  • OpenAI — text-embedding-* models via API
  • Gemini — models/embedding-* via Google API
📊
Two Vector Stores
Both implement VectorStore ABC: add(chunks), search(embedding, top_k), persist(), load(), clear().
  • ChromaDB — PersistentClient, cosine space, upsert
  • FAISS — IndexFlatIP (inner product = cosine for L2-norm)
  • FAISS JSON sidecar for metadata persistence
  • ChromaDB auto-persists; FAISS needs explicit persist()
🗂
4-Tab Streamlit UI
All pipeline controls live in the sidebar. Tabs handle ingestion, retrieval demo, evaluation runs, and system status — with shared session state across tabs.
  • Ingestion — upload, chunk preview, index build
  • Retrieval Demo — run queries, inspect ranked results
  • Evaluation — load ground truth, run metrics, download CSV
  • System Status — METRICS snapshot, health indicators

Evaluation Metrics

Four standard IR metrics computed per query and averaged across the ground-truth set. All are doc-id-based with deduplication before scoring.

🔍
Recall @ K
Fraction of relevant documents found within the top-K results. For a single-relevant-document setup this is equivalent to Hit@K.
hits / |relevant|
🎯
Precision @ K
Fraction of the K retrieved results that are relevant. Denominator is always K, not the number of results returned.
hits / K
🏆
MRR
Mean Reciprocal Rank — the reciprocal of the rank of the first relevant result. Rewards systems that surface the right answer early.
1 / rank_of_first_relevant
📈
nDCG @ K
Normalised Discounted Cumulative Gain. Accounts for rank position — relevant docs ranked higher contribute more. Normalised against ideal ordering.
DCG / IDCG (binary relevance)

Security & Observability

Local-first design with runtime metrics, latency tracing, and safe default modes.

🔒
Security Design
  • Mock mode as mandatory default — no credentials required
  • API keys read from environment variables only
  • No user data sent externally in mock or HuggingFace modes
  • File upload validation before write (size + extension)
  • PII redaction flag available at pipeline level
  • All persistence is local-only (no cloud storage)
🔌
Observability
  • METRICS singleton tracks total_queries, total_documents, total_chunks
  • Latency tracked via timer() context manager (wall-clock)
  • Per-operation latency stored in METRICS.latencies dict
  • System Status tab exposes live METRICS snapshot
  • Health indicators: index built, provider, store, chunker
  • Error counts surfaced in evaluation summary dict

Testing & Reliability

Every stage ships with a standalone smoke test covering normal paths, edge cases, and error paths.

🧩
Stage-gated Smoke Tests
Each stage has a self-contained smoke test (_stageN_smoke_test.py) that exercises every code path before the next stage begins. Tests run from the repo root with no test runner required.
  • 10 smoke test files across 10 build stages
  • End-to-end pipeline test with real ChromaDB instance
  • Metric correctness verified against manual calculations
  • EvaluationError / RetrievalError / VectorStoreError paths tested
🛠️
Edge Cases Covered
All metric functions are tested against empty inputs, k=0, k > len(retrieved), multi-relevant documents, and degenerate ranking orders.
  • nDCG deduplication: same doc_id across chunks normalised
  • FAISS sentinel index -1 handled gracefully
  • ChromaDB metadata flattened (no None, nested dicts, lists)
  • Ground truth loader handles both relevant_doc_id and relevant_doc_ids formats

Project Scope

Deliberate constraints keep the project focused on retrieval evaluation, not RAG kitchen-sink demos.

✓ This project IS
  • ✓A retrieval evaluation framework with IR metrics
  • ✓A pluggable chunking + embedding + vector store pipeline
  • ✓A local-first, offline-capable system (mock default)
  • ✓A Streamlit app for interactive exploration
  • ✓A ground-truth-based benchmark harness
  • ✓Export-ready: CSV results, pandas DataFrames
✗ This project IS NOT
  • ✗An LLM inference / generation system
  • ✗A chat interface or conversational agent
  • ✗A FastAPI or REST service
  • ✗MCP / CrewAI / LangChain stack
  • ✗Kubernetes or cloud-deployed infrastructure
  • ✗BM25 or hybrid sparse retrieval (v1 scope)
